# DevDeck 1.49.1

## The whole window stuttered while sessions worked in the background

With a deck of many sessions the UI froze for seconds at a time — a click on a row answered eight seconds later, the terminal you were typing in stopped echoing — while the process list showed DevDeck using almost no CPU on average.

- **Measured on the running app** (v1.49.0, 20 tiles, 8 of them on another PC): single frames of 5 to 16 seconds, 27 to 55 seconds of the UI thread blocked in a minute, in six episodes over one afternoon. Each matched the time someone was at the PC while sessions they were not looking at were printing.
- **Cause.** Every tile is its own terminal, and all but the selected one are `display: none`. xterm pauses a terminal it cannot see, but only on the path output takes. A scrolled line also asks the terminal's selection to refresh, and the DOM renderer answers that by drawing every row again — paused or not. So a session working in the background redrew its whole hidden screen for every line it printed. And a hidden terminal is the slowest thing that renderer can draw: it sizes each cell by measuring its character in a helper span and remembers the answer unless the answer is 0, which is what every measurement inside a `display: none` subtree returns. Nothing was remembered; each redraw measured every cell again, each measurement a write followed by a layout read — 0.37 ms apiece in a 21,000-node document, 1,400 to 3,800 cells a screen. That is 0.5 to 1.4 seconds per hidden tile per scrolled frame. The CPU profile of one stall: 8.9 of 9.0 seconds in that one measurement.
- **Switching sessions paid it too**: the terminal being left is hidden first and blurred a frame later, and a blur redraws every row — up to a second on each switch.
- **Fix.** A tile that is not on screen draws nothing (`src/renderer/hiddenTerminal.ts`). The skipped work is one full refresh, which xterm does when the tile is shown again; its buffer was always current, so nothing is lost. The same deck then measures 4 character-width measurements where it measured 122,533, and no long task where it had one of 179 ms with only two tiles open.

This has been there since the terminal moved to xterm's DOM renderer (1.38.0); it grows with the number of sessions working out of sight, which is why a deck of four never showed it.

## The performance gate was not measuring what it said

`qa/perf-gate.mjs` waited for the fixture agents to finish with a `waitForFunction` whose predicate was `async`. The promise it returned was taken for the answer, and a promise is truthy: every wait returned at once. The "working" window measured the 4 ms after the key was sent rather than the 8 seconds of repainting, on every CI run since the gate was added.

- The gate now reads what each fixture agent has finished from a log the agent writes, and fails if the working window was not the 8 seconds it is meant to be.
- A new **hidden** phase: both sessions scroll 60 lines while one is behind the other, counted in character-width measurements (independent of the runner's speed), plus a check that the hidden tile shows its output the moment it is selected. It fails on 1.49.0 with 122,533 against a limit of 300.
- The gate's window keeps drawing when another window covers it. Windows does not draw a covered window at all, so on a desktop in use every number passed for having measured nothing.
