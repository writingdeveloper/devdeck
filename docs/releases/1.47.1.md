# DevDeck 1.47.1

## Closing a background session works when Claude Code's background service is off

Closing a Claude Code background session from the sidebar (1.46.0) could fail with "Could not close the background session '…' — try claude rm <id> in a terminal", on this PC and on a paired one alike.

- **Cause:** `claude stop` and `claude rm` talk to Claude Code's background service, an on-demand daemon that exits 50 s after its last client — and a Claude Code update leaves none behind. With no service running, Claude Code 2.1.312 answers `couldn't remove <id> — the background service may be restarting. Try again in a moment.` and does not start one. Trying again in a moment does not help; opening `claude agents` once does, because that starts the service. DevDeck's log only said `failed`; the reason was on stderr, which it did not read.
- **Fix:** when `rm` refuses, DevDeck starts the service the way Claude Code itself does (`claude daemon run --origin transient` — it ends itself once idle, so nothing is left running), waits for `claude daemon status` to see it, and runs `stop` and `rm` once more. A session that is already gone counts as closed. What `rm` said is now in the diagnostics log.
- **The message names the right PC.** The failure toast told you to run `claude rm <id>` "in a terminal" even when the session was on another PC, where the command has to run; on this PC it answered `No job matching`. It now names that PC, and says that opening `claude agents` there once starts the service.

Verified on Windows with Claude Code 2.1.312: with the service stopped, `stop` and `rm` on a session waiting for input both refused with the message above; after `claude daemon run` they answered `stopped <id>` and `removed <id>`; the transient service exited on its own 50 s later. A paired PC gets the fix when its DevDeck updates.
