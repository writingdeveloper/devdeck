# 실사용 버그 예방 검토 — 1.37.5

## 결론

2026-09-07 검토 시작 시 기존 테스트는 **1,242개 통과, 1개 생략**이었다. 그러나 비동기 응답의 순서, 화면 수명, 저장 성공 여부를 결합한 실제 사용 시나리오에는 결함이 있었다. 테스트 수를 늘리는 것보다 **사용자 행동 → 실제 IPC → 저장/네이티브 기능 → 화면 결과 → 재시작 후 결과**를 검증하는 것이 중요하다.

## 확인하여 수정한 결함

| 상황 | 기존 문제 | 변경 |
|---|---|---|
| 머신 A에서 B로 전환, 응답 지연 | B 이름 아래 A의 프로젝트와 실행 버튼이 남음 | 선택 즉시 프로젝트·선택·비용·사이드바 초기화 |

| 활성 터미널을 가진 앱 종료 | Link 기능 검사가 성공해도 호스트 종료 코드가 3221226356 | 네이티브 터미널 종료 이벤트를 기다린 뒤 앱 종료, QA에서 종료 코드도 확인 |

## 기존 QA가 놓친 이유

1. **함수의 결과와 사용자의 최종 결과가 다르다.** 단위 테스트는 작업 배열 계산을 검증하지만, 실패한 저장이 화면·디스크·재시작 사이에서 어떻게 보이는지는 확인하지 않았다.
2. **순차 성공 흐름의 편중.** 실제 사용에서는 응답 순서가 뒤집히고, 요청 도중 화면/머신이 바뀌며, 같은 화면을 다시 방문한다. 머신 ID만 검사하는 방어는 A → B → A를 막지 못한다.
3. **QA와 릴리즈가 분리되어 있었다.** CI는 단위 테스트와 접근성·일부 IPC 검사를 실행했지만 화면 사용 흐름과 Link 검사는 수동이었다. 태그 릴리즈 작업에는 테스트 의존성이 없었다.
4. **배포 형태 검증 부재.** 개발 모드의 성공만으로 패키지의 네이티브 모듈·에셋·preload 구성이 정상이라고 단정할 수 없다.
5. **실제 환경에 의존하는 QA 데이터.** 현재 저장소·사용자 대화·설치된 CLI에 따라 결과와 부작용이 달라질 수 있었다.

## 이번에 추가한 예방 장치

- `npm run qa:resilience`: 실제 Electron 앱에서 디스크 실패, 초안 보존, 재시도, 재시작 후 영속성, 요청 응답 역전, 머신 삭제, Windows 네이티브 터미널을 검증한다. 응답은 임의의 지연 시간에 기대지 않고 검사에서 직접 순서를 제어한다.
- 사용자 데이터와 분리한 임시 프로필·Git 저장소를 사용한다. 새 실패 복구 QA의 터미널은 고정 출력의 테스트 CLI로 실행해 실제 AI 세션이나 로그인에 의존하지 않는다.
- CI에 Linux/Windows 실패 복구 QA와 Linux 다국어 화면 사용 흐름 검사를 추가했다. 실패 시 결과 JSON과 화면을 실행 아티팩트로 남긴다.
- 릴리즈는 공통 CI 전체 성공 후 OS별 설치 파일을 만든다. Windows 패키지의 실행 파일로 실패 복구 QA를 다시 실행한다.
- 세 OS의 패키징까지 모두 성공한 뒤 파일을 하나의 비공개 초안에 모아 공개한다. 태그와 패키지 버전도 대조한다.
- 종료 중에는 새 터미널 생성을 거부하고, 이미 닫는 중인 터미널까지 종료 이벤트를 기다린다. 비정상 종료 코드도 QA 실패로 취급한다. 기다림은 제한 시간을 두어 종료가 영원히 멈추지 않게 한다.
- 의존성 점검에서 발견한 `fast-uri`, `@xmldom/xmldom`, `nanoid`의 취약 버전을 호환되는 패치 버전으로 갱신했다. 갱신 직후 `npm audit` 보고는 0건이다. CI에도 높은 심각도 이상 의존성 경고를 실패시키는 검사를 추가했다.

### 수정 전 재현 확인

동일한 새 실패 복구 QA를 기존 `v1.37.4` 커밋의 별도 체크아웃에서도 실행했다. 디스크 쓰기를 실패시켰을 때 사용자에게 실패가 표시되지 않아 첫 저장 복구 시나리오가 실패했다. 수정한 버전에서는 같은 검사에서 초안 보존·재시도·재시작 후 저장 확인이 통과했다.

종료 문제는 본 프로젝트의 Link 실행에서 관찰한 비정상 종료 코드가 근거다. 참고로 upstream에도 Electron 종료 중 네이티브 콜백 정리 경쟁에 관한 [별도의 보고](https://github.com/microsoft/node-pty/issues/904)가 있다. 해당 보고는 macOS 사례이므로 이 Windows 오류의 원인이 완전히 동일하다고 단정하지 않는다.

## 검증 운영 기준

새 버그 수정에는 가능하면 **수정 전 버전에서 실패하는 재현 시나리오**를 먼저 만든다. 기대값은 내부 상태의 모양보다 사용자가 보는 결과와 재시작 후 데이터를 기준으로 잡는다.

| 변경 영역 | 최소 검증 |
|---|---|
| 파서·순수 계산 | 정상·빈 값·손상 입력·경계값 단위 테스트 |
| 비동기 화면 | 성공/실패 응답 역전, 반복 방문, A → B → A |
| 저장 작업 | 실패, 재시도, 중복 클릭, 재시작, 허용 범위 변경 |
| 머신·세션 | 연결 종료/복구, 호스트 재시작, 세션 중복/유실, 권한 변경 |
| UI | 실제 클릭·키보드·한/영/일/중·좁은 폭·접근성 |
| 릴리즈 | 동일 커밋의 모든 게이트, OS별 빌드, 실제 패키지 실행 |

## 남은 위험과 후속 우선순위

이 릴리즈가 모든 예외 상황을 없앤다는 의미는 아니다. 다음은 현재 검증으로 보장하지 못하는 범위다.

- **높음 — 여러 클라이언트의 동시 편집:** 작업 목록 API는 여전히 배열 전체를 저장한다. 두 머신이 같은 프로젝트의 작업을 동시에 수정하면 마지막 쓰기가 앞선 편집을 덮을 수 있다. 후속으로 버전 비교 저장 또는 작업별 변경 API와 충돌 안내가 필요하다.
- **높음 — 장시간·실제 네트워크 환경:** 절전/재개, VPN 주소 변경, 네트워크 단절, 두 머신의 수일 사용은 짧은 CI 실행으로 완전히 대체되지 않는다. 기존 `qa:link`와 `qa:perf`를 실제 Windows 환경에서 유지하고 장시간 검사를 별도로 운영해야 한다.
- **중간 — 설치·자동 업데이트 전체 경로:** 이번 게이트는 패키지 실행 파일을 검사한다. NSIS 설치 마법사, 기존 설치에서의 업데이트 적용, OS별 서명/권한 흐름은 별도 검증이 필요하다.
- **중간 — macOS/Linux 실제 데스크톱:** 세 OS에서 빌드/단위 테스트를 실행하고 Linux에서 화면을 검사하지만, macOS GUI·외부 터미널 사용자 흐름까지 자동화하지는 않았다.
- **중간 — 추가 저장 설정 UI:** 메모·작업·프로젝트 상태의 실패 처리를 보강했다. 다른 설정 화면도 저장 실패 시 입력 보존·재시도 동작을 같은 기준으로 순차 확장할 필요가 있다.

QA 결과는 CI 실행 아티팩트 및 로컬 `qa/shots/`에서 확인한다. 릴리즈 공개 여부와 OS별 결과는 해당 태그의 Release 실행을 최종 근거로 사용한다.
